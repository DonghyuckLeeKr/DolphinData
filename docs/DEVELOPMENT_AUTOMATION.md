# DolphinData 개발 자동화 (이 PC에서 시작)

## 흐름

1. 사용자: 앱 설정 → 문제 진단 및 접수 → 기록 시작 → USB 재연결 등 문제 동작 → **기록 종료하고 문제 접수**. 앱에서 접수 번호를 확인합니다. 내용 확인과 JSON 백업은 선택 사항입니다.
2. 관리자: 자동 접수한 리포트를 이 PC의 관리자 화면과 지정 디스코드 채널에서 확인합니다. 백업 파일은 관리자 화면 또는 `/dolphin-report file:`로 가져올 수도 있습니다.
3. 일일 예약 또는 관리자 계정의 자동 수정 요청으로 수정안을 준비합니다. 문제 설명과 익명화한 기록을 이 PC의 Codex에 전달해 별도 복제본에서 수정합니다. 로그인된 ChatGPT 사용량을 사용하며 계정 한도가 적용됩니다. 일반·디자인 요청은 네트워크 재연결 기록 대신 설명과 기존 화면을 참고합니다.
4. 수정 범위 검사 → 검토용 GitHub 브랜치 및 draft PR → GitHub Windows 검사 및 설치파일 생성. 자동 수정 프로세스에는 GitHub·디스코드·업데이트 서명 환경변수를 전달하지 않습니다.
5. 관리자: PR 변경 내용과 검사 설치파일을 실제 장치에서 확인 → **수정 검토 완료 · 승인**. 검사한 커밋을 main에 fast-forward로 반영합니다. Git의 원자적인 기준 커밋 확인으로 승인 중 main이 바뀌어도 덮어쓰지 않습니다. main이 바뀌었다면 새 기록 요청으로 다시 검사해야 합니다. 저장소에 추가 브랜치 보호 정책이 있으면 이 단계가 거절될 수 있습니다.
6. 관리자: **이 버전 배포 승인**. GitHub `production` 환경 승인을 처리한 후 서명된 자동 업데이트와 설치파일을 빌드·배포합니다. 이 단계의 빌드는 같은 코드에 대해 다시 수행하므로 검토용 설치파일과 파일 해시는 다를 수 있습니다.

승인하지 않은 수정본은 사용자에게 배포되지 않습니다. 디스코드 버튼은 서버 ID·채널 ID·본인 계정 ID가 모두 일치해야 동작합니다. 역할 이름이나 표시 이름을 승인 근거로 사용하지 않습니다. 승인 이력에 코드 커밋, 수정본 SHA256, 승인 계정과 시간을 남깁니다.

## 접수를 모아서 처리

- 접수는 수정 작업과 관계없이 최대 200건까지 보관합니다. 접수 즉시 AI 작업을 시작하지 않고 관리자 요청 또는 일일 예약 때 처리합니다.
- 원하는 시점에 관리자 화면에서 **함께 처리할 접수로 선택**을 체크하고 **선택한 접수 함께 수정**을 누릅니다. 한 번에 서로 다른 2~10건을 하나의 수정안·PR·검사 설치파일로 묶습니다.
- 디스코드에서는 관리자 계정으로 `/dolphin-batch`를 실행하고 최근 대기 접수 중 2~10건을 선택합니다. 선택하면 수정이 시작됩니다. 전체 설명과 더 이전의 접수는 관리자 화면에서 확인합니다.
- 검토 중인 수정안에 연결된 접수, 기존 일괄 처리에 포함된 접수는 중복 선택할 수 없습니다. 작업 중 새로 들어온 접수는 다음 처리 대상으로 남습니다.
- 일괄 수정 카드에 포함된 접수별 설명과 AI 처리 결과가 표시됩니다. AI는 접수별 변경 또는 미해결 이유를 정리하며, 검사 성공이 모든 요청의 해결을 뜻하지는 않습니다. 실제 요구 충족 여부는 관리자가 검토합니다.
- 수정 승인과 배포 승인은 각 일괄 수정안에 대해 한 번씩 진행합니다. 모든 접수의 익명화한 재생 검사는 동일한 수정본에 포함하고, 버전도 한 번만 올립니다. 문제 설명은 공개 PR·재생 검사에 포함하지 않습니다.
- 변경을 만들지 못했거나 PC 종료로 중단되면 같은 일괄 수정 카드에서 다시 요청합니다. 접수 연결은 재시작 후에도 유지하며 중단 작업은 자동 실행하지 않습니다.
- GitHub에서 반영하지 않고 닫은 수정안은 **접수 대기로 돌리기**로 다시 선택할 수 있습니다. 이전 PR·코드·승인 이력은 보존합니다. 닫힌 일괄 수정안을 대기로 돌리면 포함된 접수들을 다시 개별 선택할 수 있습니다. 이미 반영된 수정안은 대기로 돌리지 않습니다.
- 닫힌 일괄 수정안의 **같은 묶음 다시 수정**은 접수 연결과 일일 실행 기록을 유지하고, 이전 코드·PR을 이력으로 남겨 새 시도로 수정·검사를 진행합니다. 실패한 검사 결과를 승인으로 바꾸거나 예약이 자동 재시도하지 않습니다. 이미 반영된 수정안은 재시도하지 않습니다.
- AI 수정 작업은 한 번에 하나씩 실행합니다. main이 바뀌면 기존 수정본을 새 기준으로 다시 검사해야 하며, 이전 코드에 대한 승인으로 새 코드를 배포하지 않습니다.

## 매일 오후 9시 자동 수정

- 새 `received` 접수 중 자동 처리에 포함되고 충분한 기록이 있는 건을 오래된 순으로 최대 10건 선택합니다. 1건이면 개별 수정, 2~10건이면 하나의 일괄 수정안으로 처리합니다. 초과 접수와 작업 중 새 접수는 다음 처리 대상으로 보관합니다.
- 이전 수정안의 검사·수정 승인·배포 승인이 끝나지 않았다면 그날 새 수정은 보류합니다. 실패·중단·추가 확인 요청은 자동 재시도하지 않으며 관리자가 확인합니다. 대기 접수가 없는 날은 AI를 실행하지 않습니다.
- 한국 날짜별 실행 예약을 AI 실행 전에 저장합니다. 같은 날 중복 호출, PC 재시작, 시작 도중 중단 후에도 AI를 다시 시작하지 않습니다. 그날 확인 후 들어온 접수는 다음 일일 실행 또는 수동 요청에서 처리합니다.
- Windows 검사에 성공하면 디스코드에 **새 승인 요청 메시지**를 보냅니다. 검사 커밋별로 한 번만 요청하며 승인 버튼은 해당 커밋에 연결됩니다. 검사 실패 시 승인 버튼을 보내지 않습니다. 수정·배포 승인은 관리자가 각각 진행합니다.
- 공개 접수 주소와 Discord `/dolphin-report`로 들어온 접수는 **검토 전** 상태로 일일 자동 처리에서 빠집니다. 내용을 확인한 뒤 관리자 화면 또는 Discord 카드의 **일일 자동 처리에 포함**을 눌러야 예약 실행 대상이 됩니다. 이 PC의 관리자 화면에서 직접 올린 접수만 바로 포함됩니다.
- 관리자 화면의 **일일 자동 처리에서 제외**로 검증용 접수 등을 제외할 수 있습니다. 제외해도 접수·설명을 보관하고 수동 처리는 가능합니다.
- 이 PC와 Codex 앱, `Start-Automation.cmd`가 실행 중이어야 합니다. 디스코드 연결·Codex 로그인·GitHub 검사·배포 승인 설정이 필요합니다. 로컬 예약의 운영 조건은 [Codex 공식 안내](https://learn.chatgpt.com/docs/automations)를 참고합니다.
- 실행 도구는 현재 Windows 계정으로 암호화한 `admin-access.dpapi`를 읽어 로컬 관리자 API에만 접속합니다. `Start-Automation.cmd`가 서버 시작 때 이를 갱신합니다. 키·토큰을 예약 프롬프트에 넣지 않습니다. `-PreviewOnly`는 선택 대상만 확인하며 AI와 실행 이력을 변경하지 않고, `-StatusOnly`는 예약·최근 작업 상태만 조회합니다.

## 최초 운영 준비

- Node.js 22+, Git, GitHub CLI, Codex CLI가 필요합니다. `codex login`과 `gh auth login`을 먼저 완료합니다. Codex CLI는 `--ignore-user-config`, `--ignore-rules`, `--ephemeral` 옵션을 지원해야 합니다. 현재 PC의 CLI 0.162.0-alpha.17.2에서 확인했습니다.
- Windows에서는 Codex의 기본 Agent sandbox 설정을 먼저 완료해야 합니다. 자동 수정은 사용자 설정 파일을 제외하므로 실행 인자로 `windows.sandbox="elevated"`를 지정해 Windows sandbox 구현을 활성화합니다. `workspace-write` 파일 범위와 네트워크 제한은 유지합니다. 구성에서 이 항목이 빠지면 로그인에 성공해도 조회·편집 명령이 차단될 수 있습니다.
- 이 변경을 main에 반영해야 GitHub `preview-windows.yml` 검사 작업이 등록됩니다. 이후 새 PR마다 해당 커밋의 Windows 검사가 자동 실행됩니다. 관리자 화면에 준비 상태가 표시됩니다.
- 저장소 Settings → Environments → `production`: required reviewers에 관리자를 지정하고, 혼자 운영하는 경우 본인 실행 승인 금지를 해제합니다. 관리자 화면과 봇은 승인자가 없는 환경에서는 코드 승인도 거절합니다.
- 기존 GitHub `TAURI_PRIVATE_KEY`, `TAURI_KEY_PASSWORD`가 업데이트 서명에 사용됩니다. 일반 Windows 실행파일의 인증서 서명과는 별개입니다.
- `automation/Start-Automation.cmd` 더블클릭. 처음에는 봇 라이브러리를 설치하고 관리자 브라우저를 자동으로 엽니다. HTML 파일을 직접 열거나 미리보기로 보면 실제 목록에 연결되지 않습니다. 실행 창의 로컬 주소에는 임시 관리자 키가 있으므로 공유하지 않습니다. 같은 탭에서 새로고침해도 인증이 유지되며 서버를 다시 시작한 뒤에는 새 실행 창의 주소를 사용합니다.
- `npm run automation`으로 디스코드 없이 관리자 화면만 실행할 수도 있습니다.

파일과 수정본은 `%LOCALAPPDATA%\DolphinData\automation`에 보관합니다. 관리자 서버는 `127.0.0.1:4174`, 접수 전용 서버는 `127.0.0.1:4175`입니다. PC가 꺼져 있거나 도구가 종료되면 리포트 접수와 버튼 처리는 중단됩니다. GitHub 검사는 계속되며 재실행하면 결과를 확인합니다. 진행 중 로컬 수정이 중단되면 자동 재시도하지 않습니다.

## 다른 사용자 PC에서 자동 접수

- 관리자가 `automation/Enable-FreeIntake.cmd`를 한 번 실행합니다. Cloudflare 공식 릴리스의 SHA256을 검증하고 연결 도구를 관리자 PC에 설치합니다. 봇 토큰이나 관리자 키는 앱에 넣지 않습니다.
- `Start-Automation.cmd`를 실행하면 접수 전용 포트만 무료 Quick Tunnel에 연결합니다. `4174` 관리자 화면·목록·수정·승인 기능은 외부 연결하지 않습니다.
- 연결이 확인되면 GitHub CLI로 main의 `support/diagnostic-intake.json` 파일만 갱신합니다. 이 파일에는 공개 HTTPS 접수 주소만 있습니다. 앱은 매 접수 시 이 주소를 다시 확인하므로 연결 도구 재시작으로 주소가 바뀌어도 새 설치파일이 필요하지 않습니다. GitHub 로그인과 이 파일의 쓰기 권한이 필요합니다.
- 이 파일 갱신도 main 커밋을 만들므로 자동 수정 중에는 도구를 재시작하지 않는 것이 좋습니다. 기준 main이 바뀌면 기존 수정본 승인은 거절되며 새 요청이 필요합니다.
- Quick Tunnel은 초기 운영과 테스트용이며 가동 시간을 보장하지 않습니다. 고정 주소와 상시 운영이 필요해지면 Cloudflare 계정·도메인의 정식 터널 또는 별도 접수 서버로 전환해야 합니다. [공식 안내](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/).
- 접수 API는 256KB 이하의 엄격한 진단 형식만 받고 분당 30건·동시 4건으로 제한합니다. 성공하면 리포트 내용이 없는 접수 번호만 반환합니다. 접수만으로 자동 수정이나 배포는 실행하지 않습니다.
- 같은 리포트의 재전송은 저장·디스코드 카드 한 건으로 처리합니다. 전송 실패 시 앱에 익명화한 리포트를 보관하며, 다음 실행에서도 ‘다시 접수’를 누를 수 있습니다.
- 자동 접수가 계속 실패하면 앱에서 백업 JSON을 저장해 `donghyucklee.kr@gmail.com`으로 첨부해 전달할 수 있습니다.

## 디스코드 설정

1. [Discord Developer Portal](https://discord.com/developers/applications)에서 애플리케이션과 봇을 만들고 서버에 초대합니다. `bot`, `applications.commands` 범위를 사용합니다.
2. 설치 범위는 `bot`, `applications.commands`, 권한은 View Channel, Send Messages, Embed Links, Read Message History를 선택합니다. 비공개 승인 채널은 ‘멤버 또는 역할 추가’에서 봇 역할도 허용해야 합니다. 관리자 권한은 필요하지 않습니다. Guilds intent만 사용하며 Message Content 등 privileged intents는 필요하지 않습니다.
3. 디스코드 개발자 모드를 켜고 서버·리포트 채널·본인 계정 ID를 복사합니다. 리포트에는 사용자의 설명이 첨부파일로 포함될 수 있으므로 채널 접근 권한을 제한해주세요.
4. `automation/Set-Discord.cmd` 더블클릭. 토큰은 화면에 표시되지 않는 보안 입력으로 받고 Windows DPAPI로 암호화해 이 PC에 저장합니다. 토큰을 채팅·소스·GitHub 이슈에 붙여 넣지 않습니다.
5. `automation/Start-Automation.cmd` 더블클릭. 봇이 지정 서버의 `/dolphin-report`, `/dolphin-batch` 명령을 등록합니다. 파일 접수, 개별·일괄 수정, 수정 승인, 배포 승인을 이 채널에서 진행합니다.

단순 Discord webhook은 알림만 지원합니다. 승인 버튼은 Gateway 봇 연결을 사용합니다. 앱의 외부 자동 접수는 별도의 접수 전용 터널을 사용하며 공유기 포트 개방은 필요하지 않습니다. 모바일 디스코드에서도 승인 버튼을 누를 수 있습니다.

## 데이터 범위 및 검증 한계

- 진단 기록은 기본으로 꺼져 있습니다. 같은 상태는 연결 확인에 필요한 두 번만 저장하고, 이후 상태가 바뀌면 계속 저장합니다. 최근 240개를 보관하며 오래된 기록이 빠지면 부분 기록으로 표시합니다. 한도 도달로 종료하지 않습니다. 설정을 닫아도 계속 기록하며 직접 종료·접수 또는 앱 종료 후 추가 수집하지 않습니다.
- 네트워크 이름, 장치 식별값, 어댑터 이름, 게이트웨이를 리포트별 별칭으로 대체합니다. 실제 사용량·요금제 이름·SIM 번호는 내보내지 않습니다. 기존 사용량·기준 사용량·일별 기록의 존재를 작은 고정값으로 표현합니다.
- Windows 버전·CPU 아키텍처와 설치된 USB 네트워크 드라이버의 버전·USB VID/PID(기종 식별용 공통값)를 포함합니다. 장치별 일련번호나 전체 PnP ID는 포함하지 않습니다. 권한·드라이버에 따라 수집에 실패하면 이 부분은 비어 있을 수 있습니다.
- 사용자가 입력한 설명의 일반적인 IP·MAC·이메일·SIM 형태 번호·Windows 사용자 경로를 가리지만 임의의 개인정보를 모두 찾을 수는 없습니다. 접수 전 설명을 확인해주세요. 설명은 지정된 비공개 디스코드 채널과 관리자 화면에 표시합니다. 관리자가 자동 수정을 요청하면 설명을 AI에 전달합니다. 설명을 명령으로 취급하지 않으며 공개 PR 본문·진단 재생 테스트에는 넣지 않습니다. 충분히 긴 설명이 그대로 수정 파일에 복사된 경우 공개를 중단합니다.
- 기록 재생은 실제 앱의 네트워크 확인·분류 함수를 호출합니다. 익명화로 인한 정보 제한이 있으며 실제 USB 드라이버, SIM 교체, 부팅 자동 실행, ETW 권한을 재현하지 않습니다. 검사 성공만으로 해당 하드웨어 동작이 입증되지는 않습니다.
- 자동 수정이 허용되는 파일은 `src`의 JS/JSX/CSS, `src-tauri/src`의 Rust, `tests`의 JS 테스트입니다. 의존성·워크플로·자동화 코드 변경은 수동 개발 대상으로 남깁니다. 한 번에 최대 30개 파일, 512KB 변경을 허용합니다.
- 자동 수정은 20분 안에 끝나야 합니다. 근거가 부족하면 변경을 만들지 않고 AI의 처리 이유를 표시합니다. 검토용 커밋·PR이 아직 만들어지지 않은 실패·중단 요청은 같은 리포트에서 다시 요청할 수 있습니다. 시도마다 새 복제본을 만들며 이전 기록은 보존합니다. 검토용 PR이 생성된 요청은 중복 실행하지 않으며 기존 PR은 수동으로 닫습니다.
- 관리자 로컬 프로세스와 Codex는 동일한 Windows 사용자로 실행됩니다. Windows sandbox는 실행 경계를 제공하지만 별도 운영체제/VM 격리는 아닙니다. 운영을 확대할 때는 전용 Windows 계정 또는 별도 워커로 분리하는 것이 좋습니다.
